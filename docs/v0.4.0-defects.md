## D-001 — Delegated member could commit household Smart Funding

- **Severity:** P1 (security / delegated-authority hardening)
- **Area:** `server/app/budgeting_routes.py` → `commit_smart_funding`
- **Observed:** `commit_smart_funding` gated only on the `assign_money` capability. Unlike `upsert_assignment` and `transfer_allocation`, it had no explicit `DelegatedBudgetPolicy` check. A delegated member was only prevented incidentally, because a restricted month summary returns `ready_to_assign = 0` (no proposals). That is a data-shape coincidence, not an authorization boundary.
- **Expected:** A delegated member must never allocate household Ready-to-Assign, even if capability configuration would otherwise permit it. Delegated authority comes only from the funded pool.
- **Root cause:** The explicit delegated-policy guard added to the ordinary assignment/transfer routes was not mirrored on the Smart Funding commit route.
- **Fix:** Added an explicit `DelegatedBudgetPolicy` lookup immediately after the capability check; a member with a policy receives `403 "Delegated members allocate only from their delegated pool"` before any summary/preview is computed.
- **Test coverage:** `test_delegated_access.py::test_delegated_member_cannot_commit_smart_funding_against_household_rta` — grants the delegate `assign_money` + `move_money` + a real policy, seeds household RTA, asserts the commit is `403` and household RTA is unchanged.
- **Status:** FIXED.

## D-002 — Swift `InsightsCalculator` semantics diverged from canonical server analytics

- **Severity:** P1 (financial-report consistency)
- **Area:** `Sources/BudgetCore/Insights.swift`
- **Observed:** The Swift calculator counted **any** positive amount as income (so refunds inflated income), and `spendingByCategory` ignored refunds and split-only contributions. The server (canonical) treats a positive categorized amount as a refund that *reduces* spending and never as income.
- **Expected:** Swift and server must share one definition. Transfers excluded. Income = uncategorized on-budget inflow only. Categorized negatives = spending; categorized positives = refunds that reduce spending. Split portions attributed exactly.
- **Root cause:** The Swift library type predated the server analytics semantics and was never realigned (it is not yet wired into a shipping screen, but is a latent trap and had tests asserting the wrong behavior).
- **Fix:** Rewrote `spendingByCategory` (net = Σ −amount per category; omit non-positive-net categories; include contributing IDs for purchases and refunds) and `incomeVersusSpending` (income = uncategorized positive; spending = Σ −amount over categorized/split portions). Semantics now match `server/app/analytics_routes.py`.
- **Test coverage:** `Tests/BudgetCoreTests/InsightsTests.swift` — added `testRefundReducesSpendingAndIsNotCountedAsIncome` and `testExpandedSplitPortionsAreAttributedExactly`; existing rolling-period, transfer-exclusion, and category-change tests retained. *(Swift tests are authored but not executed on this host — see Mac/Xcode acceptance items.)*
- **Status:** FIXED (server-executed parity verified indirectly via server suite; Swift unit run pending macOS).

## D-003 — Server refund netting in analytics reports

- **Severity:** P1 (financial correctness, aligns server to canonical definition)
- **Area:** `server/app/analytics_routes.py` → `spending_report`, `income_spending_report`
- **Observed:** `spending_report` skipped all positive amounts (`amount_minor >= 0`), so a categorized refund did not reduce the category's spending. `income_spending_report` summed only negative categorized amounts, so refunds were silently dropped from the spending figure.
- **Expected:** Refunds (positive categorized/split amounts) net against spending; categories whose net spending is ≤ 0 are omitted from the ranking; contributing transaction IDs include both purchases and refunds.
- **Fix:** Spending loop now skips only transfers and zero amounts, nets `totals[category] -= amount`, omits non-positive-net categories, and totals from the positive rows. Income-vs-spending computes net spending over categorized/split portions.
- **Test coverage:** existing `test_analytics.py::test_spending_report_is_explainable_and_split_aware` and `test_income_spending_excludes_transfers_and_recalculates_after_edit` still pass; the Swift refund test mirrors the same numbers.
- **Status:** FIXED.

## D-004 — Insights drill-down showed stale totals after an edit

- **Severity:** P1 (stale UI after successful financial mutation)
- **Detected by:** source trace of the Insights drill-down path.
- **Area:** `ios/BudgetApp/BudgetWorkspaceView.swift` → `LiveReportCategoryView`
- **Observed:** The category detail held a captured `APISpendingCategoryReport` value. After editing a transaction out of the category and returning, `refresh()` updated `store.spendingReport`, but the detail view still displayed the snapshot total/rows until popped and re-entered.
- **Expected:** The drill-down total and contributing rows recalculate as soon as the underlying report refreshes.
- **Root cause:** View bound to a value snapshot instead of the live store row.
- **Fix:** `LiveReportCategoryView` now re-derives its name/total/contributing IDs from `store.spendingReport` (matched by `categoryID`), falling back to the passed snapshot only before the report has loaded; shows an empty state when the category no longer has spending in range.
- **Test coverage:** logic verified by source; runtime confirmation is `MAC-INSIGHTS-EDIT` in the acceptance script.
- **Runtime verification needed?** Yes (SwiftUI).
- **Status:** FIXED (source).

## D-005 — Delegated Plan offered guaranteed-403 actions

- **Severity:** P2 (UX / permission alignment; server already safe)
- **Detected by:** delegated client UX audit (Part 10).
- **Area:** `ios/BudgetApp/BudgetWorkspaceView.swift` → `LivePlanView`
- **Observed:** Smart Funding and the category assignment editor were gated only on `can("assign_money")`. A delegated member holding a `DelegatedBudgetPolicy` is always 403-blocked from both on the server, so the UI could present a guaranteed-failure path.
- **Expected:** Delegated members reallocate via Move money; household assignment/Smart Funding are not shown.
- **Fix:** Both are now additionally gated on `store.delegatedBudget == nil`.
- **Runtime verification needed?** Yes (SwiftUI, delegated persona).
- **Status:** FIXED (source).

## D-006 — Structured server error messages were swallowed

- **Severity:** P1 (error propagation / financial conflicts)
- **Detected by:** API client error-handling audit (Part 14).
- **Area:** `Sources/BudgetAPI/APIModels.swift` → `APIErrorBody`
- **Observed:** `detail` was decoded as `String?`. Reconciliation mismatch, allocation/request version conflict, and stale-balance responses return `detail` as an object (`{"message": ..., ...}`). Those failed to decode, so the client fell back to a generic HTTP status string and the user never saw "Refresh and try again" / "Cleared balance does not match statement".
- **Expected:** Actionable server messages surface for both string and object `detail` shapes.
- **Fix:** Custom `APIErrorBody` decoder accepts a string `detail` or an object with a `message`.
- **Test coverage:** `APIClientTests.testStructuredConflictDetailSurfacesActionableMessage` and `testStringConflictDetailStillSurfacesMessage` (authored; require Swift toolchain / Mac to execute).
- **Runtime verification needed?** Swift unit run on Mac.
- **Status:** FIXED (source).

## Observations logged (not fixed — acceptable or Mac-gated)

- **O-1 (P2):** `load()` fetches requests/allowances/delegatedBudget/forecast/members with `try?`, so a transient failure silently yields empty/nil. Acceptable graceful degradation for optional surfaces, but a failed `requests` fetch briefly hides pending approvals and a failed `/delegated-budgets/me` makes a delegate render as non-delegated until the next refresh. Consider distinguishing 404 (no policy) from transient errors. Mac-verify.
- **O-2 (P3):** `format()` and chart math use `Double(minor)/100` for display only; all stored/mutated money is exact `Int64`. No money is computed in floating point. No action needed.
- **O-3 (P2):** Demo data source computes report spending as `abs(amount)/splitCount` and does not net refunds, so demo Insights are approximate for uneven splits/refunds. Live path is exact (server). Demo-fidelity only.
- **O-4 (Mac):** Dates use the local Gregorian calendar consistently (`dateString`, `FinancialPeriodCalculator(.current)`); confirm on a device whose timezone is not UTC that a transaction dated "today" does not shift a calendar day.
