# v0.6 Insights Implementation Plan

Status: **IN PROGRESS**

This plan implements the v0.6 Insights milestone without changing the authoritative ledger,
allocation, reconciliation, or forecast semantics. The server owns financial classification and
exact integer-minor-unit aggregation. Swift Charts consumes report DTOs and may convert exact totals
to floating-point values only for presentation geometry.

## Delivered foundation

- Spending Breakdown is transaction-backed, split-aware, refund-netted, transfer-excluding, filtered,
  permission-scoped, and drillable through the shared transaction editor.
- Income vs. Spending totals use the same server classification and retain contributing transaction IDs.
- Date, account, category/group, member, payee, type, clearing, and tracking filters are available where
  supported by the canonical report contract.

## Checkpoints

### 1. Income and spending trends

- [x] Server-authoritative monthly periods within any inclusive requested range.
- [x] Exact income, spending, difference, and contributing transaction IDs per period.
- [x] Partial first/last calendar months are explicitly bounded by the requested dates.
- [x] Swift API contract and native Swift Charts visualization.
- [x] Demo/live contract parity.
- [x] Regression coverage for splits, refunds, transfers, boundaries, and chart presence.

### 2. Net worth

- [x] Server-authoritative historical net worth series.
- [x] Visible-account and tracking-account scope with exact account contributions.
- [x] Assets, liabilities, total net worth, filters, and account drill-through.
- [x] Native accessible chart and meaningful empty states.

### 3. Budget and target performance

- [x] Assigned versus spent and category availability context.
- [x] Target funding/performance explanations without treating targets as money.
- [x] Overspending, RTA, rollover, and recommended-funding context from canonical planning data.
- [x] Category drill-through using existing production report/transaction views where a category has contributing activity.

### 4. Interaction and closure

- [ ] Time-point selection and transaction/account drill-through across all reports.
- [ ] Filter parity audit (tags/flags/reconciled where product contracts support them).
- [x] Restricted-member aggregate/privacy regression matrix for report resources, member filters, and mixed visible/hidden aggregates.
- [ ] Performance/load coverage for long histories.
- [ ] Full backend, package, native, UI, accessibility, dark mode, and human acceptance.

## Non-goals

- No predictive advice, bank connectivity, scenario mutation, or client-owned financial definitions.
- No report may mutate transactions, allocations, balances, targets, schedules, or reconciliation state.
- No v0.6 engineering checkpoint constitutes human acceptance or release tagging.
