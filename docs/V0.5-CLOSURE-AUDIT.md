## Delivered

- Household-owned payees have stable identities, normalized names, archive state, aliases, per-budget
  default-category suggestions, authorized history statistics, rename, and explicit merge.
- Payee selection is server-authoritative and searchable. Activity filtering selects an existing
  identity only; transaction create/edit may resolve or create a new identity at save. Initial/recent
  results and subsequent pages are bounded to 20, aliases participate in matching, archived identities
  are excluded from transaction selectors, and scoped members receive only identities already visible
  through authorized transactions. Workspace hydration no longer downloads the household's full payee
  history.
- Migration `0018_first_class_payees` losslessly backfills legacy non-system payee strings and leaves
  punctuation variants distinct. Transactions retain their original display string and gain a nullable
  payee identity. System, reconciliation, opening-balance, and transfer rows do not become user payees.
- Scheduled transactions now retain a nullable first-class payee identity. Rename and merge preserve
  future schedule identity, and realization resolves the current canonical payee without changing any
  forecast or financial semantics.
- Activity uses a server-authoritative, permission-filtered transaction browser with text search, typed
  filters, deterministic sorting, authorized counts, and stable cursor pagination.
- Flags and tags are normalized, searchable, filterable, visible in registers/details, and editable in
  the shared editor. Bulk cleared/uncleared, flag, and tag changes validate the entire selection before
  one commit, reject reconciled/hidden/system-linked rows, and write actor-attributed change records.
- Ordinary transactions can be duplicated through the normal financial engine. Copies receive a new
  identity and explicit date, are uncleared, omit attachments, preserve exact splits/payee/flag/tags,
  and rebuild category/card-reserve consequences exactly once. Specialized/system-linked rows are
  rejected.
- Payee management and recent authorized transaction drill-through live in the canonical workspace.
  Demo and Live use the same views, application services, and repository contracts.
- One-way VOID preserves the original as `VOIDED` and creates a bidirectionally linked, current-date
  `REVERSAL` with exact opposite amount/splits. Actor, timestamp, and reason are retained. Transfers and
  reconciled rows are rejected rather than partially or silently mutated.
- Make Recurring leaves the posted transaction untouched and creates a new future-only schedule using
  calendar-aware day/week/month/year advancement. The next occurrence remains editable and no forecast
  template affects actual balances before realization.
- PDF, JPEG, PNG, and HEIC attachments are authorized at the transaction boundary and stored as
  AES-GCM encrypted managed objects. Metadata contains stable identity, sanitized display name, media
  type, size, and SHA-256—not a host filesystem path. Limits are 10 MB per object and 20 objects per
  transaction. Detach tombstones for 30 days before garbage collection; void retains attachments.

## Financial and authorization findings

- Search and payee aggregates first reduce to the member's effective account/category dataset. Hidden
  rows do not contribute to results, counts, filters, suggestions, or statistics.
- Search and metadata bulk changes are money-neutral. Duplicate routes through ordinary transaction
  creation, including exact split and funded-card reserve behavior.
- Existing expense, income, categorized refund, split, transfer, card payment, reconciliation, schedule
  realization, edit, and delete engines were not replaced.

## Schema and migration

`0018_first_class_payees` adds `payees`, `payee_aliases`, `payee_budget_preferences`, and nullable
`transactions.payee_id`. `0019_txn_rev_attach` adds lifecycle/linkage fields and
attachment metadata. `0020_payee_identity_repair` links post-0018 textual transactions that were saved
without a first-class identity, including the human-observed `Metadata test` row, while continuing to
exclude transfers, opening balances, reconciliation adjustments, and reversals. Forward migration preserves transaction/allocation observations and does not merge
ambiguous punctuation variants. Focused migration-graph/populated-upgrade plus financial-vector tests pass (18/18
combined; 13 are golden vectors).
`0021_scheduled_payee_id` adds a nullable scheduled-transaction foreign key and index, linking only
unambiguous active canonical or alias matches. It creates or merges no payees, and leaves unmatched
schedule text intact.

## Post-closure human acceptance correction — rotated credentials

Human overnight testing found that an already-mounted Live workspace could retain its construction-time
access token after `AppSession` successfully rotated to a new token. The workspace route keeps the same
budget identity across rotation, so SwiftUI may preserve its `StateObject` while rebuilding a view that
already observes the new token; the prior `onChange` callback then has no transition to deliver.

All long-lived Live snapshot and command repositories now share one mutable credential owner, resolve
the current token at request time, and use one client factory. Workspace loading is keyed to the session
token so the current credential is bound even on a post-rotation initial render. Attachment loading is
keyed to the credential generation, cancels superseded work, and suppresses cancellation errors rather
than issuing repeated stale requests or presenting an attachment-specific alert. Live-shaped regression
coverage proves attachment list A → credential rotation → attachment list B → Make Recurring B without
reconstructing the store. Human overnight/background acceptance remains required.

Follow-up human lunch-idle testing showed that mutable storage alone was insufficient: Activity was
the first caller after expiry, and transaction search had no path that asked `AppSession` to rotate the
credential. It therefore sent the last workspace token twice as SwiftUI replaced the selected tab's
lazy navigation composition. The Live workspace now binds its shared credential owner to AppSession's
single-flight refresh gateway. Snapshot loads and every command resolve that authority immediately
before execution; concurrent identical transaction-browser loads coalesce in the long-lived store.
Native regression coverage uses an expired token, rotates it without reconstructing the workspace,
opens concurrent Activity searches, and proves exactly one search with only the new bearer token.
Human lunch/overnight acceptance remains required.

## Runtime diagnostic investigation — 2026-09-15

The recurring console diagnostic `cannot add handler to 0 from 0 - dropping` was investigated rather
than suppressed. It is not present in Budget App source or its checked-in dependencies. Unified-log
records identify the emitter as the current application process calling Apple's QuartzCore framework:

- subsystem: `com.apple.coreanimation`
- category: `API`
- sender image: `/System/Library/Frameworks/QuartzCore.framework/QuartzCore`
- format string: `cannot add handler to %i from %i - dropping`
- message type: error

The two zeroes are therefore values supplied to a private Core Animation diagnostic format, not Budget
App object, account, transaction, or handler identifiers. The stripped framework does not expose the
private integer-state names, so their more specific meaning is not asserted.

Budget App log correlation found the diagnostic during ordinary SwiftUI navigation, tab transitions,
list scrolling, text-field interaction, and sheet transitions. It was also observed before any
attachment interaction in a production-composition UI-test run. The corresponding navigation,
keyboard, scrolling, swipe-action, attachment-source, and Quick Look tests completed successfully; no
missed input, stuck presentation, duplicate request, crash, or accessibility failure correlated with
the message. Source review found no application-created Core Animation completion-handler registry.
The UIKit bridges used for camera capture and Quick Look retain their coordinators for the controller
lifetime and dismiss/complete through one delegate path. Attachment source presentation continues to
use the already-tested queued handoff after the source confirmation dialog dismisses; no presentation
state was weakened or bypassed during this investigation.

For independent reproduction, a temporary dependency-free SwiftUI probe was compiled with Xcode 27.0
Beta (`27A5252f`) and run on the preserved iPhone 17 Pro Max / iOS 27 simulator
(`3ABD861E-D38D-4AFD-A356-959266051564`). The probe contained only a `TabView`, `NavigationStack`,
`List`, `TextField`, and sheet, and automatically exercised tab changes, navigation push/pop, and sheet
present/dismiss. Its own process emitted the same QuartzCore subsystem/category/format diagnostic at
the corresponding transitions. It contains no Budget App code, dependencies, attachment code,
Photos picker, file importer, Quick Look integration, or custom gesture handling. This independently
reproduces the diagnostic in Apple's Xcode 27/iOS 27 SwiftUI/Core Animation stack.

**SOURCE IDENTIFIED: YES.** Apple's QuartzCore/Core Animation `API` logger emits the message.

**APPLICATION DEFECT: NO.** No Budget-specific cause or user-visible failure was found, and the same
message is independently reproducible without Budget App code.

**APPLE BETA ISSUE: CONFIRMED.** The diagnostic itself is reproducible in a minimal Xcode 27 Beta / iOS
27 Apple-framework-only application. This finding does not claim that every possible animation or
presentation failure is harmless.

**USER-VISIBLE IMPACT:** None observed. In the tested flows the diagnostic only adds console noise;
navigation, sheets, keyboard entry, scrolling, swipe actions, attachment source presentation, Quick
Look preview, and app lifecycle behavior continued to work.

**ACTION TAKEN:** No console suppression, arbitrary delay, or production behavior change. Reopen this
finding if it coincides with a missed animation completion, stalled or duplicate presentation, failed
tap/gesture, stuck keyboard, Quick Look/Photos/Files failure, sustained frame loss, accessibility
failure, crash, or reproducible behavior difference on a stable iOS runtime or physical device.
