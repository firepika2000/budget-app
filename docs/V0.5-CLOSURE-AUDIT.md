# v0.5 Transaction System + Payees — Engineering Closure Audit

## Delivered

- Household-owned payees have stable identities, normalized names, archive state, aliases, per-budget
  default-category suggestions, authorized history statistics, rename, and explicit merge.
- Migration `0018_first_class_payees` losslessly backfills legacy non-system payee strings and leaves
  punctuation variants distinct. Transactions retain their original display string and gain a nullable
  payee identity. System, reconciliation, opening-balance, and transfer rows do not become user payees.
- Activity uses a server-authoritative, permission-filtered transaction browser with text search, typed
  filters, deterministic sorting, authorized counts, and stable cursor pagination.
- Flags and tags are normalized, searchable, filterable, visible in registers/details, and editable in
  the shared editor. Bulk cleared/uncleared, flag, and tag changes validate the entire selection before
  one commit, reject reconciled/hidden/system-linked rows, and write actor-attributed change records.
- Ordinary transactions can be duplicated through the normal financial engine. Copies receive a new
  identity and explicit date, are uncleared, omit attachments, preserve exact splits/payee/flag/tags,
  and rebuild category/card-reserve consequences exactly once. Specialized/system-linked rows are
  rejected.
- Payee management and recent authorized transaction drill-through live in the canonical workspace.
  Demo and Live use the same views, application services, and repository contracts.
- One-way VOID preserves the original as `VOIDED` and creates a bidirectionally linked, current-date
  `REVERSAL` with exact opposite amount/splits. Actor, timestamp, and reason are retained. Transfers and
  reconciled rows are rejected rather than partially or silently mutated.
- Make Recurring leaves the posted transaction untouched and creates a new future-only schedule using
  calendar-aware day/week/month/year advancement. The next occurrence remains editable and no forecast
  template affects actual balances before realization.
- PDF, JPEG, PNG, and HEIC attachments are authorized at the transaction boundary and stored as
  AES-GCM encrypted managed objects. Metadata contains stable identity, sanitized display name, media
  type, size, and SHA-256—not a host filesystem path. Limits are 10 MB per object and 20 objects per
  transaction. Detach tombstones for 30 days before garbage collection; void retains attachments.

## Post-closure human acceptance correction — rotated credentials

Human overnight testing found that an already-mounted Live workspace could retain its construction-time
access token after `AppSession` successfully rotated to a new token. The workspace route keeps the same
budget identity across rotation, so SwiftUI may preserve its `StateObject` while rebuilding a view that
already observes the new token; the prior `onChange` callback then has no transition to deliver.

All long-lived Live snapshot and command repositories now share one mutable credential owner, resolve
the current token at request time, and use one client factory. Workspace loading is keyed to the session
token so the current credential is bound even on a post-rotation initial render. Attachment loading is
keyed to the credential generation, cancels superseded work, and suppresses cancellation errors rather
than issuing repeated stale requests or presenting an attachment-specific alert. Live-shaped regression
coverage proves attachment list A → credential rotation → attachment list B → Make Recurring B without
reconstructing the store. Human overnight/background acceptance remains required.
