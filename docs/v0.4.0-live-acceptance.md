## Findings

### Finding 1 — Fresh Budget Plan dead end *(v0.4 acceptance BLOCKER)*

A newly created live Budget contains no category groups or categories. The Plan screen
correctly renders the empty financial state but exposes **no discoverable action** to create
the first category group/category. The Focus menu contains only filters — All, Underfunded,
Overspent, Funded, Available — and no category management.

**Impact:** a brand-new live household can create a Budget but cannot progress into normal
budgeting from the Plan UI without an external/API workaround. This violates the
production-completeness and human-acceptance gates.

**Classification:** v0.4 acceptance blocker. The Plan empty state must provide a discoverable
path to create the first category group/category (see the v0.4 milestone and First-Budget
Experience requirement in the roadmap). This is a functional first-run onboarding gap, not the
polished guided tour.

**Engineering resolution — fixed, human retest pending.** `LivePlanView` now renders a "Build
your first plan" empty state (headline, explanation, and a prominent **Create Category Group**
primary action) whenever a loaded Budget has zero groups and zero categories and the user holds
`manage_budget_structure`. The action opens the existing production `CategoryCreationView` sheet —
which, with no groups present, creates the first group and first category together through the live
`createCategoryGroup`/`createCategory` API — so no onboarding-only category engine was introduced.
After creation the normal grouped Plan renders and the `+` toolbar menu remains the discoverable
path for further groups/categories. (Note: the `+` "Add category" menu already existed and is
shown to owners; the defect was discoverability on an empty screen, which the empty state fixes.)

### Finding 2 — Owner-specific empty-state wording *(v0.4 UX defect)*

Immediately after owner authentication, the Budgets empty state displayed wording equivalent
to *"No shared budgets / Ask the household owner to share a budget with this account."* The
authenticated user **was** the household owner, and did have a working `+` action and
successfully created a Budget — so functionality exists, but the copy is contextually
incorrect and confusing for an owner during fresh-budget onboarding.

**Classification:** UX defect to correct during fresh-budget onboarding closure. The empty
state should distinguish an owner (who can create a Budget) from a member awaiting a shared
Budget.

**Engineering resolution — fixed, human retest pending.** `BudgetListView`'s zero-Budget state is
now capability-aware. A user who owns an active household (`canCreateBudget`, the same signal that
gates the `+` action) sees *"No budgets yet / Create your first budget to start organizing your
household's money."* with a **Create Budget** action; a member without that authority still sees the
shared-budget guidance. Behavior is driven by the existing household-ownership signal, not a new
hard-coded role check.

### Finding 3 — iOS first-time bootstrap submission returned 422 *(defect requiring diagnosis)*

The first bootstrap attempts from the iOS setup form returned `422 Unprocessable Entity`.
A direct request built from the documented backend contract succeeded with `201 Created`.

Backend bootstrap requires: `email`, `password` (minimum 12 characters), `display_name`,
`household_name`. The iOS form **did** contain a Household Name field, so this is **not** a
simple missing-household-field defect.

**Root cause — identified (was unknown at first report).** The iOS request encoding is **correct**:
`BootstrapRequest` maps `display_name`/`household_name` via `CodingKeys`, verified by a new encoding
test. The request is not a DTO/mapping defect. The 422 was a **client-side validation gap**: the
setup form enforced only non-empty fields, so a password shorter than the backend's 12-character
minimum was submitted. Confirmed empirically against the live app — an 11-character password returns
`422` with a FastAPI validation **array** (`detail: [{loc, msg}]`, msg "String should have at least
12 characters"), while a valid password returns `201`. Two compounding issues: (a) no pre-submission
length check, and (b) the client's error decoder handled only string/object `detail`, not the 422
array, so the error surfaced as a generic "unprocessable" string.

**Engineering resolution — fixed, human retest pending.** The setup form now enforces the contract
before submission (password ≥ 12 with inline guidance, email length ≥ 3, non-blank display/household
names) and keeps the primary action disabled until a request would validate. The shared client's
`APIErrorBody` now also parses the FastAPI 422 array into a readable, field-labelled message
(e.g. *"Password: String should have at least 12 characters"*) without exposing raw Pydantic
`type`/`loc` internals. A valid iOS submission reaches `201` and authenticates with no curl/API-docs
workaround.

### Finding 4 — `GET /delegated-budgets/me` returned 404 for the owner *(semantic review)*

During initial hydration, `GET …/delegated-budgets/me` returned `404 Not Found` while the
authenticated user was the household owner. Other hydration calls succeeded.

This may be legitimate API semantics ("this user has no delegated budget") or an
integration/empty-state issue. Recorded as a **finding requiring review**, not a declared bug.
Related open item: [v0.4.0 Mac acceptance](v0.4.0-mac-acceptance.md) O-1 (whether a failed
`requests` / `/delegated-budgets/me` fetch should surface an error rather than silently
degrade).

**Review conclusion — confirmed intentional behavior; client already handles it cleanly. No change
required.** `GET /delegated-budgets/me` returns `404 "Delegated budget not found"` by design when
the caller has no delegated budget (an owner never does), while the collection `GET
/delegated-budgets` returns `200` — confirmed empirically (`404` for `/me`, `200` for the list). The
iOS workspace already loads `/me` with `try?`, so a `404` resolves to `delegatedBudget == nil`, which
renders the normal owner "Available to assign" Plan rather than any error or corrupted state. The
API contract and delegated-authority semantics are unchanged; a client test now locks that a `404`
surfaces as `server(404)` (→ nil) rather than a decode failure or a swallowed success. This is a
distinct concern from Mac O-1, which is about whether other silently-degraded fetches should instead
show an error — that remains a separate UX judgment call, not a correctness bug here.

### Finding 5 — Authentication refresh concurrency / session recovery *(defect)*

During live relaunch, the app displayed a *"Something went wrong / Invalid or expired refresh token"*
alert while still showing the authenticated Budgets UI. The server log for that relaunch (summarized)
was:

```
POST /api/v1/auth/refresh  -> 200
POST /api/v1/auth/refresh  -> 401
POST /api/v1/auth/refresh  -> 401
GET  /api/v1/me            -> 200
GET  /api/v1/budgets       -> 200
```

So the original refresh token was valid, one refresh succeeded and its new access token was usable
(`/me` and `/budgets` returned `200`), and additional concurrent refreshes used the now-rotated token
and failed — the losing `401` surfaced a user-visible error even though authentication had already
recovered. This is a refresh-token rotation race.

**Root cause.** `AppSession.refreshIfNeeded` read the stored refresh token and only wrote the rotated
token *after* the network `await`. On relaunch, multiple independent session-initialization paths —
`loadBudgets()` reached via `configureServer`/`validateSelectedSource` (both `RootView.task` and the
`scenePhase == .active` handler) plus `BudgetListView.task`, and direct `refreshIfNeeded` calls in
the workspace/detail views — each ran that read-then-write concurrently, so each submitted the same
`R1`. The backend rotated `R1→R2` for the winner (`200`) and rejected the stale `R1` for the losers
(`401`), and a loser's `401` propagated to `errorMessage`.

**First engineering fix (`e17c100`) — single-flight + generation-safe refresh.** Refresh was made
single-flight and generation-safe:

- At most one `/auth/refresh` is in flight per session; concurrent callers await the same shared task
  and receive the same rotated tokens. The check-and-install of the shared task runs synchronously on
  the main actor, so no second caller ever submits the old refresh token.
- Credential writes are serialized and carry a monotonic generation; a refresh result — success or
  failure — is applied only while its generation is still current, so a stale success cannot clobber
  newer tokens and a stale failure cannot clear credentials a newer refresh installed. This is
  enforced by generation, not by inspecting error strings.
- A recovered refresh no longer surfaces any user-facing error.
- A genuinely invalid/expired refresh token (with no competing success) clears credentials and
  transitions cleanly to Sign In, preserving the Live Budget Server selection and never falling back
  to the deterministic demo.

Automated coverage was added in the app test target (`ios/BudgetAppTests/AppSessionRefreshTests.swift`):
concurrent refresh issues exactly one request and keeps the rotated credentials with no error;
concurrent `loadBudgets` at startup issues one refresh and lands Connected; a genuine `401` clears to
Sign In while preserving Live server selection; and a stale success arriving after sign-out does not
re-authenticate. The transport is a deterministic gated mock (no sleeps).

**Mac human retest of `e17c100` — FAILED (not PASS).** Built and run on an iPhone 17 Pro Max
Simulator (iOS 27.0), on a launch whose stored refresh token had already been invalidated by the
earlier pre-fix race (so this exercised the genuine-invalid recovery path). The app again showed
*"Something went wrong / Invalid or expired refresh token"* over a stale authenticated-looking Budgets
screen. The server log for this launch was:

```
GET  /api/v1/health          -> 200
GET  /api/v1/health          -> 200
GET  /api/v1/bootstrap/status -> 200
GET  /api/v1/bootstrap/status -> 200
POST /api/v1/auth/refresh    -> 401
POST /api/v1/auth/refresh    -> 401
POST /api/v1/auth/refresh    -> 401
```

Three sequential refresh `401`s and duplicated discovery — a *failed invalid-session recovery*, distinct
from the original rotation race (do not conflate the two log blocks). `e17c100`'s single-flight only
collapses callers overlapping the in-flight `refreshTask` window; it did not make invalidation a
terminal, authoritative state, and it left two startup weaknesses that multiplied the load.

**Root cause of the recovery failure.** Refresh eligibility was gated only by the mutable
`refreshToken`/access-token freshness, with no authoritative "session invalidated" latch. Two
independent startup entry points — `RootView`'s `.task` and its `scenePhase == .active` handler —
each ran `validateSelectedSource → configureServer → (health, bootstrap) → loadBudgets → refreshIfNeeded`
(hence the duplicated `/health` and `/bootstrap/status`). Worse, `configureServer` published
`connectionStatus = .connected` *before* the authenticated load resolved, so `RootView` rendered
`BudgetListView` in the not-yet-loaded window — showing stale content and spawning that view's own
`loadBudgets → refreshIfNeeded`. Because these loaders were staggered behind different `await` chains
and eligibility was re-evaluated across the credential-clearing boundary, more than one `/auth/refresh`
went out for the already-invalid token, and the invalid session was not presented as Sign In.

**Second engineering fix (this task) — make invalid-session recovery terminal.**

- **Authoritative terminal latch (`authInvalidated`).** A current-generation refresh `401` latches the
  session invalid; `refreshIfNeeded` is then a no-op until a successful login/bootstrap/invitation
  resets it (in `save`). Eligibility is now "Live, not invalidated, has credentials" — a caller
  arriving after the failed refresh cannot begin a new refresh for the dead generation. This is a
  state gate, not a delay/retry-count/error-string check.
- **No premature `.connected`.** `configureServer` stays `.connecting` until `loadBudgets` resolves,
  so the Budgets UI (and its loader) is never presented during the authenticated-but-not-yet-loaded
  window. `loadBudgets` publishes `.connected` on success or `.authenticationRequired` on an invalid
  refresh, so a failed recovery routes straight to Sign In with no stale Budgets.
- **Coalesced startup validation.** `validateSelectedSource` is single-flight, so the `.task` and
  `scenePhase` entry points share one discovery + one authenticated load (removing the duplicate
  `/health` and `/bootstrap/status`).
- **401 is an auth transition, not an error.** The handled refresh `401` is consumed at the session
  boundary and never sets `errorMessage`; stale `budgets`/`profile` are cleared; Live server
  URL/source are preserved; no demo fallback. Other network/server errors still surface normally.

New regression coverage (same test file): sequential post-failure callers issue exactly one refresh and
stay invalidated with cleared budgets and no error; the concurrent startup composition (two
`validateSelectedSource` entry points) runs discovery and refresh exactly once — a test that would have
failed on `e17c100`'s duplicated discovery; and a successful login after invalidation restores a
refreshable session.

**Status: Engineering fixed / second human retest pending.**

### Finding 6 — SwiftUI "Publishing changes from within view updates" warning *(separate; deferred)*

During the same human test, Xcode logged: *"Publishing changes from within view updates is not
allowed, this will cause undefined behavior."* This is a synchronous `@Published` mutation during a
SwiftUI view-update pass. It is **not** the same defect as Finding 5 — the refresh race sets state
from async continuations *after* an `await`, not within a view update — and it was not conclusively
attributed to the refresh path here. The invalid-session-recovery correction removed one synchronous
startup state publish (the premature `.connected` in `configureServer`), which may incidentally reduce
startup publishing, but the audit did **not** conclusively tie the warning to the authentication/session
sequencing, so it was not treated as the same root cause. **Status: recorded, deferred to a separate
UI-stabilization task.** It should be reproduced on a Mac (Xcode purple-runtime breakpoint) to capture
the exact publishing call site before fixing.
