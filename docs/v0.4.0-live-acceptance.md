## Findings

### Finding 1 — Fresh Budget Plan dead end *(v0.4 acceptance BLOCKER)*

A newly created live Budget contains no category groups or categories. The Plan screen
correctly renders the empty financial state but exposes **no discoverable action** to create
the first category group/category. The Focus menu contains only filters — All, Underfunded,
Overspent, Funded, Available — and no category management.

**Impact:** a brand-new live household can create a Budget but cannot progress into normal
budgeting from the Plan UI without an external/API workaround. This violates the
production-completeness and human-acceptance gates.

**Classification:** v0.4 acceptance blocker. The Plan empty state must provide a discoverable
path to create the first category group/category (see the v0.4 milestone and First-Budget
Experience requirement in the roadmap). This is a functional first-run onboarding gap, not the
polished guided tour.

### Finding 2 — Owner-specific empty-state wording *(v0.4 UX defect)*

Immediately after owner authentication, the Budgets empty state displayed wording equivalent
to *"No shared budgets / Ask the household owner to share a budget with this account."* The
authenticated user **was** the household owner, and did have a working `+` action and
successfully created a Budget — so functionality exists, but the copy is contextually
incorrect and confusing for an owner during fresh-budget onboarding.

**Classification:** UX defect to correct during fresh-budget onboarding closure. The empty
state should distinguish an owner (who can create a Budget) from a member awaiting a shared
Budget.

### Finding 3 — iOS first-time bootstrap submission returned 422 *(defect requiring diagnosis)*

The first bootstrap attempts from the iOS setup form returned `422 Unprocessable Entity`.
A direct request built from the documented backend contract succeeded with `201 Created`.

Backend bootstrap requires: `email`, `password` (minimum 12 characters), `display_name`,
`household_name`. The iOS form **did** contain a Household Name field, so this is **not** a
simple missing-household-field defect.

**Root cause is not yet known.** Candidate causes to diagnose include client-side validation
and request encoding/field mapping. This is recorded as a v0.4 acceptance defect requiring
diagnosis; no root cause is claimed here.

### Finding 4 — `GET /delegated-budgets/me` returned 404 for the owner *(semantic review)*

During initial hydration, `GET …/delegated-budgets/me` returned `404 Not Found` while the
authenticated user was the household owner. Other hydration calls succeeded.

This may be legitimate API semantics ("this user has no delegated budget") or an
integration/empty-state issue. Recorded as a **finding requiring review**, not a declared bug.
Related open item: [v0.4.0 Mac acceptance](v0.4.0-mac-acceptance.md) O-1 (whether a failed
`requests` / `/delegated-budgets/me` fetch should surface an error rather than silently
degrade).
