# v0.4.0 functional audit

Audit date: 2026-09-04  
Baseline: `v0.3.0` (`87517c1`)  
Device: iPhone 15 Pro Max simulator, iOS 17.5, Xcode 15.4

## Audit method

The committed application was built with `xcodebuild`, installed, launched, and visually inspected in Simulator. Each primary destination was launched from a clean process. Mutation paths were then traced from the SwiftUI control through its store or API call and compared with server routes and domain invariants. Build success is recorded separately from functional status.

## Executive finding

The v0.3.0 native product experience is a deterministic, in-memory demo and is not the authenticated self-hosted product. Debug builds open `DemoRootView` unless launched with `--live`; the five-tab experience reads and mutates `DemoStore`, while live users receive the older budget-list/detail interface. This split is the root cause behind most “looks complete but is not complete” behavior.

The accounting server remains the stronger part of the product. The immediate stabilization requirement is to make status honest, repair broken demo workflows for review, and converge on a single production-domain source of truth rather than adding more disconnected showcase screens.

## Independent correction verification (2026-09-05)

The follow-up independent review is **confirmed in substance**. The v0.4 branch had added a much broader server-backed `LiveBudgetRootView`, but this was still a second product implementation beside `DemoRootView`. That work improved production behavior but did not satisfy the required architecture. Feature-surface work is paused until one shared interface is driven by interchangeable repositories.

### Root causes

1. Presentation architecture forked at `RootView`, making the deterministic demo a different application rather than a data source.
2. Resource authorization and monetary authorization were treated as the same concept, although visibility does not establish a spending/allocation ceiling.
3. Several financial mutations lacked a first-class application service and immutable change record, leaving UI code to perform selective refreshes and demo-only arithmetic.
4. Reconciliation modeled the physical correction as a transaction but did not separately authorize or classify its budget consequence.

### Release decision

Correction status: **ENGINEERING GATES COMPLETE; HUMAN REVIEW REQUIRED**. `DemoRootView` and `LiveBudgetRootView` were removed. `BudgetWorkspaceView` and `BudgetWorkspaceStore` now drive both authenticated and deterministic modes. Automated financial, API, migration, and native tests pass; the final gate is the documented hands-on live and persona review.

## Data consistency findings

1. `DemoStore` is a single observable object, so local mutations generally refresh all demo screens. That is useful architecture but not persistence.
2. Live mutations in the older interface use independent view state and selective reloads, so a single invalidation/repository boundary is still needed.
3. Several demo operations silently return on validation failure. The user sees neither the violated invariant nor a retry path.
4. Several displayed values are hard-coded rather than derived, including the Home forecast low point, report summaries, and portions of approval previews.
5. Demo reset replaces all arrays, confirming that the product shell is intentionally ephemeral.

## Permission findings

- Presentation filtering hides parent accounts/categories from Alex and Mia in the demo.
- This filtering is not security: selecting a persona does not authenticate another member and `DemoStore` contains the complete household dataset in-process.
- The server already enforces resource grants for existing endpoints. New delegated category and allocation operations must be added and tested server-side; SwiftUI visibility alone is insufficient.
- Jordan currently receives owner-like demo visibility. Ownership-only actions must remain separately enforced in the live domain.

## Stabilization order

1. Add deterministic domain services and tests for report periods, explainable aggregates, transaction edit propagation, and delegated allocation conservation.
2. Extend the server schema/API for scoped category administration and delegated authority rules with authorization-bypass tests.
3. Replace silent demo mutations with typed outcomes and complete the visibly broken flows, especially reconciliation, transaction types/editing, splits, and request decline.
4. Introduce one app repository/invalidation boundary that can use persisted local storage or a self-hosted API while driving the same native shell.
5. Complete Insights drill-down and delegated persona UX on that shared domain.
6. Run the complete simulator persona walkthrough, polish, and only then consider release.
