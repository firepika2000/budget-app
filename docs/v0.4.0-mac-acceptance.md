# v0.4.0 — Mac / Xcode Acceptance Script

This is Rey's hands-on test script. Everything below requires the Xcode Simulator and/or an authenticated live server — it could not be verified on the Windows development host. Backend behavior is already covered by the automated suite (71 passing); this document targets the native client and end-to-end flows.

**Modes**
- **DEMO:** launch the app without `--live` (the app shows the deterministic demo workspace). Add `--demo-persona=alex` (or `mia`, `rey`, `jordan`) to pick a persona.
- **LIVE:** launch with `--live`, connect to a self-hosted server, and sign in.

**First, run the Swift unit tests** (they were authored on Windows but not executed there):
```bash
swift test
```
Expected: BudgetCore (`InsightsTests`, `MoneyTests`, etc.) and BudgetAPI (`APIClientTests`) all pass, including the new `testStructuredConflictDetailSurfacesActionableMessage`, `testStringConflictDetailStillSurfacesMessage`, `testRefundReducesSpendingAndIsNotCountedAsIncome`, and `testExpandedSplitPortionsAreAttributedExactly`.

## MAC-INSIGHTS-EDIT — Drill-down recalculates after an edit (D-004)
Mode: LIVE (or DEMO)
1. Open **Insights**. Select **30 Days**.
2. Open a category with spending (e.g. Dining).
3. Note the category **Total**.
4. Tap a contributing transaction → **Edit** → change its category to a different one (e.g. Groceries) → **Save**.
5. Navigate **back** to the category detail.

Expected:
- The category **Total** decreases by the moved amount **without leaving/re-entering** the screen.
- The moved transaction no longer appears in this category's contributing list.
- The Insights period stays **30 Days** and any filters remain selected.
- Returning to the report list shows the other category increased.
- (LIVE) The edit persists after force-quit + relaunch.

## MAC-INSIGHTS-RANGES — Period + filter wiring
Mode: LIVE
1. In Insights, cycle every period: 30/60/90 Days, 3/6 Months, YTD, 1 Year, Custom.
2. For Custom, pick an inclusive start and end.
3. Open **Filters**, set an account, a category group, a payee, a member, a type, and a cleared state; **Apply**.

Expected:
- Each period changes the totals; 30/60/90 are rolling windows ending today; YTD starts Jan 1; Custom includes both endpoints.
- Every applied filter changes the result; clearing filters restores the full report.

## MAC-DELEGATE-PLAN — Delegated Plan shows the right controls (D-005)
Mode: DEMO `--demo-persona=alex`, and LIVE as a delegated member
1. Open **Plan**.

Expected:
- A **"Your delegated budget"** section shows Total authority / Assigned / To assign.
- The **+** menu offers **Move money** (and Add category if permitted) but **not Smart Funding**.
- Tapping a category does **not** open the household assignment editor.
- Moving money between two of the member's own categories succeeds and updates both plus "To assign".
- Attempting (via any path) to exceed authority or pull from a parent category fails with a clear message.

## MAC-DELEGATE-BOUNDARY — Authority cannot be exceeded
Mode: LIVE, owner configures a $200 delegate, then sign in as the delegate
1. As owner: Household → delegated member → set authority, pool category, allow reallocation.
2. As delegate: create a category (if allowed), move money among own categories.

Expected:
- Delegate's "To assign" never exceeds the authority the owner set.
- Delegate never sees household Ready-to-Assign framing on Home/Plan.
- Delegate cannot see parent accounts, income, net worth, debt, or sibling-private categories anywhere (including Insights filters).

## MAC-ERRORS — Conflict messages are actionable (D-006)
Mode: LIVE, two devices/sessions on the same budget
1. Open the same category assignment on two sessions.
2. Change and save on session A, then save on session B (stale allocation version).
3. Reconcile an account entering a statement balance while another session clears a transaction.

Expected:
- Session B shows **"The allocation plan changed. Refresh and try again."** (not a generic "server error 409").
- Reconcile mismatch shows **"Cleared balance does not match statement"** / stale-balance message.
- No raw stack traces; messages are human-readable.

## MAC-REQUEST-APPROVAL — Full approval loop
Mode: LIVE (delegate submits, owner approves)
1. Delegate: submit a funding request.
2. Owner: open request → approve fully / partially / request changes / reject.
3. Owner: try to approve the same request twice quickly.

Expected:
- Approval moves money from the chosen source category exactly once; delegate's pool/category reflects it.
- Second decision on a finalized/updated request fails cleanly (stale version), no double funding.
- Request list, Plan, Home attention, and delegated balances all reflect the outcome after return.

## MAC-CREDIT — Card purchase / payment / edit / delete
Mode: LIVE
1. Fund a category, make a funded credit-card purchase.
2. Verify category Available drops, card balance rises, payment reserve rises.
3. Edit the purchase (change category and amount).
4. Delete a purchase.
5. Make a card payment (transfer checking → card).

Expected:
- After edit: old category restored, new category reduced, reserve rebuilt with no duplicate, card balance matches new amount.
- After delete: category restored, reserve released, card balance returns.
- Card payment reduces checking and card balance and is **not** counted as a second expense.
- (Backend equivalents are already covered by `test_credit_cards.py`.)

## MAC-PERSISTENCE — Live mutations persist
Mode: LIVE
1. Create a transaction, edit one, move money, approve a request.
2. Force-quit and relaunch; sign back in if needed.

Expected: every change is still present (server-backed). Demo mode may reset deterministically; live must not.
