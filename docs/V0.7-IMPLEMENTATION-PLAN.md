# v0.7 Daily UX + Household Experience Implementation Plan

Status: **ENGINEERING COMPLETE — HUMAN ACCEPTANCE REMAINS SEPARATE**

v0.7 makes the existing authoritative budgeting workflows comfortable for daily household use. It
does not move financial semantics into Swift, broaden delegated authority, or make Demo a separate
application. Every action continues through the shared application services and server enforcement.

## Checkpoints

### 1. Actionable Home

- [x] Capability-scoped quick actions for transaction entry, Move Money, scheduling, and requests.
- [x] Needs-attention rows that explain the issue and open the canonical resolution workflow.
- [x] Useful upcoming/recent context with intentional zero/loading/error states.
- [x] Demo/Live production-composition parity and native accessibility coverage.

### 2. Focused planning

- [x] Persisted favorite/pinned categories with stable ordering and permission-safe visibility.
- [x] Focused Plan surfaces for favorites, underfunded, overspent, funded, and available categories.
- [x] No favorite metadata may change allocations, activity, Available, or Unassigned.

### 3. Privacy presentation

- [x] Hide Amounts applies coherently to every monetary UI and accessibility value.
- [x] Privacy preference persistence and foreground/background behavior are explicit.
- [x] Screenshots, widgets, notifications, and app-switcher exposure are audited where supported.

### 4. Household access

- [x] Human-readable View Only, Limited Access, Full Access, and Custom capability mapping, with understandable account/category scope controls and deny-by-default server enforcement.
- [x] Owner-only inspection and versioned editing with last-change actor/time attribution; Full Access explicitly does not transfer household ownership.
- [x] Production Demo/Live member-detail hierarchy, current-credential repository access, scope validation, stale-edit conflict handling, and money-neutral regression coverage.
- [x] Safe invitation/member lifecycle, grant recovery, owner protection, and durable audit attribution.
- [x] Restricted users cannot discover hidden resources through selectors, counts, aggregates, or errors.

### 5. Delegation, allowances, and requests

- [x] Transparent delegated authority, limits, and funding-rule explanations.
- [x] Allowance schedule/status/history management through canonical services.
- [x] Complete request cancellation, expiration, decisions, history, and recovery lifecycle.
- [x] PostgreSQL concurrency and exact-money invariants remain green.

### 6. Guided onboarding and education

- [x] Optional, resumable, restartable guided progression through the roadmap concepts.
- [x] Prefer real interaction; any demonstration state is explicitly identified and isolated.
- [x] Contextual education explains current versus forecast money and consequence before mutation.
- [x] Dynamic Type, VoiceOver, reduced-motion, skip, and error recovery coverage.

### 7. Closure

- [x] Backend, Swift package, native XCTest, production XCUITest, migration, PostgreSQL, dark mode,
  Dynamic Type, and accessibility automation.
- [x] Human acceptance remains separately recorded and is never inferred from engineering checks.

The engineering-closure evidence and the intentionally separate human acceptance boundary are in
`V0.7-CLOSURE-AUDIT.md`.

## Non-goals

- No v0.8 loan/amortization/scenario work, v0.9 server manager, or bank connectivity.
- No local-only financial source of truth and no client-side permission substitute.
- No merge, tag, or release claim from an engineering checkpoint.
