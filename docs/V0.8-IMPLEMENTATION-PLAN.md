# v0.8 Debt Cost, Payoff, Loans & Advanced Forecasting Plan

Status: **IN PROGRESS — v0.7 engineering closed; human acceptance remains separate**

This plan incorporates the Debt Cost & Payoff product requirement without reopening engineering-
complete v0.6 or destabilizing v0.7. v0.6 remains the authoritative debt-balance/history baseline;
v0.8 adds the terms, classifications, exact projection engine, and scenario experience that the
existing model deliberately could not support.

## Financial truth boundary

- **Actual interest** is posted history with an explicit first-class interest classification. Payee
  or category-name text matching is never authoritative.
- **Estimated current interest** derives from a visible debt account's authoritative balance/principal
  and persisted terms, and is labelled estimated.
- **Projected future interest** derives from explicit scenario assumptions, and is labelled projected
  in UI, exports, and accessibility values.
- Missing terms produce `Projection unavailable / incomplete` plus the specific missing inputs.
- Editing debt terms never changes balances, posted history, reconciliation, allocations, or RTA.
- Scenario edits remain ephemeral until a separate explicit canonical planning mutation is chosen.

## Checkpoints

### 1. Contract and persisted terms

- [x] Audit debt types and define optional, type-appropriate terms for credit cards and installment
  loans without one polymorphic catch-all rule.
- [x] Persist rate representation, minimum/scheduled payment rule, frequency, due/cycle dates,
  original/remaining term, fixed/variable status, and promotional periods only where defined.
- [x] Add versioned migration, populated-upgrade/downgrade coverage, backup/restore inclusion, and
  account-metadata UI separate from reconciliation.
- [x] Missing/partial terms remain valid and describe projection readiness explicitly.

### 2. Authoritative actual-interest history

- [x] Add an explicit backward-compatible `interest_charge` transaction classification or equivalent
  ledger fact after auditing the existing transaction-type contract.
- [x] Ensure create/edit/duplicate/import/schedule/void/reversal paths preserve classification and
  accounting semantics.
- [x] Report month, YTD, trailing 12-month, and lifetime-recorded interest with explicit coverage
  dates; never infer interest from payee/category text.
- [x] Apply account/category/member privacy filtering before aggregation.

### 3. Provider-neutral exact projection engine

- [x] Define a shared deterministic engine boundary usable by Live, Demo, and future Local providers.
- [x] Accumulate currency solely in integer minor units; represent rates exactly (for example scaled
  integers/decimal input), document period conversion and cent-rounding order, and bound iterations.
- [x] Cover zero/high APR, zero balance, insufficient payment, negative amortization, frequency and
  calendar boundaries, leap years, and promotional/rate changes if those terms ship.
- [x] Return payoff date/payment count, projected interest, total projected cost, and exact
  principal/interest series—or a typed non-amortizing/incomplete result.

### 4. Multi-debt strategy comparison

- [x] Implement matching provider-neutral Python and BudgetCore strategy engines using exact integer
  minor units, deterministic monthly half-up interest, bounded iteration, and typed non-amortizing
  results. The engines support avalanche, snowball, complete explicit custom ordering, extra-payment
  scenarios, and visible rollover on/off without mutating stored financial data.
- [x] Compare avalanche (APR order), snowball (balance order), and explicit custom order without
  labelling one as best.
- [x] Make payment rollover an explicit visible assumption; support both rollover and no-rollover.
- [x] Filter inaccessible accounts and terms before ordering or totals so restricted members cannot
  infer hidden debt.
- [x] Report objective payoff order, date, remaining interest, total paid, and numerical differences.

### 5. Debt Insights experience

- [x] Add the production Payoff surface with strategy selection, explicit rollover, current-plan and
  +$50/+100/+250/custom monthly scenarios, custom priority ordering, baseline differences, typed
  incomplete/non-amortizing states, and a persistent read-only disclosure. Demo and Live use the
  same view and provider-neutral application contract.
- [ ] Extend existing Debt Insights using progressive disclosure: Overview, Actual Interest, Debt
  Cost, Payoff, What If, Strategy Comparison, and account drill-through.
- [ ] Provide bounded presets (+$50/+100/+250 per month) and exact custom input without mutating the
  budget.
- [ ] Clearly label Actual, Estimated, and Projected everywhere, including VoiceOver.
- [ ] Account detail exposes terms and readiness; reconciliation never edits APR or loan terms.
- [x] Missing-term projections provide an authorized route to the existing Debt Terms editor;
  dismissal recalculates the current scenario. Presentation is owned by the stable report root,
  with the same workspace instance. Production XCUITest covers remove → unavailable → edit/save
  → restored projection. Demo debt accounts and history now match Live's independent treatment
  of tracking loans rather than inheriting Net Worth's tracking toggle.

### 6. Verification and acceptance

- [x] A single versioned JSON fixture drives matching Python and BudgetCore strategy tests for
  avalanche, snowball, custom priority, rollover on/off, +$50/+100 scenarios, zero APR, final
  partial payments, cent rounding, and non-amortizing results using exact integer minor units.
- [ ] Complete remaining golden vectors: single/multiple cards, installment loan, mixed debts, zero/high APR,
  insufficient payment, extra payment, avalanche, snowball, custom order, rollover, cent rounding,
  month boundaries, leap year, and supported rate changes.
- [x] Guard exact-money additions and interest arithmetic against signed 64-bit overflow. Both
  providers reject out-of-range scenarios; the API returns 422 instead of unrepresentable response
  money, and Swift throws a user-readable validation error instead of trapping. A maximum-value
  zero-rate final payment remains exact. Non-custom strategies ignore duplicate unused custom-order
  values without a dictionary-construction trap.
- [ ] Authorization/privacy tests prove hidden debt contributes to no balances, terms, dates, totals,
  ordering, suggestions, error distinctions, or aggregate counts.
- [ ] Migration, populated upgrade, backup/restore, backend, Swift package, native XCTest, XCUITest,
  Dynamic Type, VoiceOver, Demo/Live parity, and exact-money gates.
- [ ] Human acceptance remains a separate gate and projections are never described as posted truth.

### 7. Insights hydration performance

- [x] Measure the production composition. Every ordinary Live workspace snapshot currently starts
  seven detailed report requests (`spending`, `spending-trends`, `income-spending`, `net-worth`,
  `debt`, `plan-performance`, and `resilience`) before Insights is opened, then fans out one target
  request per visible category and one balance request per visible account.
- [x] Separate core workspace hydration: ordinary Live activation issues zero detailed-report
  requests. Focused screens request only their required payloads; concurrent identical reads share
  a task and valid results are reused. Core refresh, date/filter/context and credential changes
  invalidate results. Report failures have independent retry and do not block Home.
- [x] Replace the hub's four on-demand detailed payloads with one bounded `/reports/summary`
  response (six scalar/currency fields, no transaction IDs or history). The server reuses canonical
  authorized reports; its internal detailed calculations are not yet optimized. Demo derives the
  same summary from its canonical snapshot definitions. Neither is a claim of CPU optimization.
- [x] Add request-count, cache/invalidation, navigation, rotated-credential, and Demo/Live parity
  coverage, including concurrent request sharing and no duplicate current-query fetch. The
  10,000-transaction summary fixture proves a bounded wire payload and no per-row SQL fan-out;
  representative timings and limitations are in the production-readiness ledger.

## Deliberate exclusions until specified

- No guessed APR, minimum-payment formula, compounding convention, promotional term, payment
  allocation rule, or historical interest classification.
- No text matching on payee/category names to manufacture actual-interest history.
- No automatic Plan/assignment mutation from a scenario and no prescriptive strategy ranking.
- No migration is applied automatically to the human Live database.
