## Current Architecture

```text
Canonical SwiftUI application
  Home | Plan | Activity | Accounts | Insights | Profile & Settings
                              |
                    BudgetWorkspaceStore
                              |
                 BudgetApplicationServices
                              |
             capability-oriented repositories
                    /                    \
       Live workspace adapter       Deterministic adapter
                    |                    |
          authenticated API          DemoStore memory
                    |
       Budget Server accounting engine
                    |
              PostgreSQL database
```

`RootView`/`AppSession` choose the source and resolve identity and an active budget. Source selection
does not choose feature views. `WorkspaceCompositionRoot` creates the appropriate repository and both
paths enter the same `BudgetWorkspaceView`. Current source choices are only **Deterministic Demo** and
**Live Budget Server**.

The command boundary covers accounts, assignments, allocation moves, transactions, linked transfers,
reconciliation, targets, schedules, requests, Smart Funding, and delegated policy. Live commands call
the server; deterministic commands mutate `DemoStore`. Workspace reads still use API-shaped snapshot
models. That is tolerable for the current incremental migration, but a local repository should not be
forced to masquerade as HTTP internally forever.

### Direct answers for real financial use today

- If **Live Budget Server** is selected, real entries live in the configured server's PostgreSQL
  database. They are durable across phone lifecycle events, but only as durable against server loss as
  the operator's database and tested encrypted backups.
- If **Deterministic Demo** is selected, entries live only in `DemoStore` process memory and reset on
  relaunch. The UI labels this source “Demo data — not authoritative” and says changes reset.
- There is no production “On this iPhone” database today. A user cannot safely choose serverless
  personal operation yet.
- There is no Dropbox-backed mode today.

### Deterministic ephemerality proof

Code evidence is conclusive:

1. `DemoStore.init()` assigns static seed arrays.
2. `DemoWorkspaceDataSource` owns a newly constructed `DemoStore`.
3. `BudgetWorkspaceStore.demo()` constructs a new deterministic data source.
4. No `DemoStore` mutation reads or writes `UserDefaults`, files, SQLite, Core Data, or SwiftData.
5. `AppSession` persists only source mode, server URL, and active-budget identity; credentials use
   Keychain. It does not persist deterministic financial state.

`AuthenticationJourneyTests.testDeterministicMutationResetsAfterProcessRelaunch` now provides the
runtime reproduction: launch the real product in Demo, change Groceries Assigned from `$720.00` to
`$820.00`, verify the in-process save, terminate the application, relaunch it, and observe `$720.00`.
This is intentional fixture behavior, not production local persistence.

## Required Production Providers

The target composition remains:

```text
Canonical UI
  -> BudgetApplicationServices
    -> repository contracts + declared capabilities
       -> LocalDeviceRepository
       -> ServerRepository (home or remote is configuration, not a new provider type)
       -> DeterministicRepository

BackupDestination (orthogonal to authority)
       -> local file / share sheet
       -> external or network storage
       -> Dropbox
```

The data source determines repository composition, authentication, availability, persistence,
synchronization, conflicts, and recovery—not navigation, editors, accounting definitions, or the
five-tab workspace. Capabilities should describe behavior such as `supportsAuthentication`,
`supportsMultipleUsers`, `supportsRealtimeSync`, `supportsLocalOnly`, `supportsBackup`,
`supportsRestore`, and `supportsHouseholdPermissions`; feature code should not switch on provider
names.

### Proposed local storage decision

Use a private, application-owned **SQLite database** behind a new `LocalDeviceRepository`, with an
explicit migration table and transactional command execution. Prefer the system SQLite library plus a
small repository-owned access layer unless the implementation stage explicitly approves GRDB. Do not
introduce SwiftData/Core Data merely to avoid defining the canonical schema.

Rationale:

- exact signed `Int64` columns and relational constraints map directly to current financial records;
- transactions can atomically update linked transfer legs and derived event records;
- forward schema migrations and restart tests can be deterministic;
- SQLite backup APIs support consistent snapshots without copying a live database file;
- a normalized schema is straightforward to encode into a provider-neutral archive and import into
  Budget Server;
- it avoids coupling portable financial identity to Apple-only object-graph metadata;
- the project already models the relational domain in PostgreSQL, while still allowing a deliberately
  smaller single-user local authority model.

This is a proposal, not an implementation decision silently committed by v0.4. Before coding, specify
the shared local accounting engine boundary so the implementation does not copy `DemoStore` arithmetic
or make the iOS client a second version of server accounting.

### Local provider minimum checkpoint

When scheduled, the first bounded checkpoint must create/open a durable local budget and persist an
account opening, group/category, assignment, cash transaction, categorized refund, linked transfer,
and reconciliation. A test must destroy all repository/service objects, reopen the same database, and
compare exact accounts, Unassigned, Assigned/Activity/Available, transaction identities, linked legs,
and reconciliation state. The same five-tab UI and editors must run unchanged.

## Data Portability

Define a versioned archive independent of SQLite, PostgreSQL, and API DTO names. Recommended logical
form: a ZIP container with `manifest.json`, newline-delimited JSON entity/event files, and an
`attachments/` tree. The manifest should contain format version, minimum reader version, export time,
source provider, household/budget stable IDs, currency metadata, content hashes, encryption metadata,
and record counts. Monetary fields remain signed integer minor units represented as JSON integers or
validated decimal strings where interoperability demands it—never binary floating point.

A complete archive must contain household/member identities appropriate to the export authority;
budgets; accounts; category groups/categories; planning periods and rollover-effective history;
allocation operations/postings; targets; schedules and realization lineage; transactions/splits;
linked transfers; reconciliation state/adjustments; credit-reserve events or sufficient canonical
source events to reconstruct them; first-class payees/aliases when implemented; requests/actions;
delegation/allowances; resource/capability grants; audit/change records; settings; notes, tags, and
attachments; plus schema/version metadata.

Import must be a validate-then-commit operation: verify archive version/hashes/references, stage it in
isolation, recompute financial invariants, report unsupported content, and commit atomically. Preserve
stable IDs and actor/audit attribution. The existing `/export.json` is useful versioned audit output,
but no supported inverse importer exists and it omits some future full-fidelity concepts; therefore it
must not be advertised as a restorable backup.

## Multi-User Authority

Local Device is single-user/single-writer. It should declare no realtime household capability. It may
store one local owner identity for attribution, but must not imitate server authorization or imply
that another device is synchronized.

Shared households require Budget Server or a future purpose-built synchronization authority. That
authority validates permissions, versions, allocation availability, and invariants; records actors;
and pushes committed changes to authorized clients. Add a versioned change feed/WebSocket notification
channel for prompt refresh. Offline display may cache the last authorized snapshot. Offline financial
mutation needs a separately designed operation queue with idempotency keys and server conflict
validation; allocation operations should not silently use stale Unassigned.

## Dropbox Recommendation

### A. Backup/restore destination — recommended first

Create an application-consistent, encrypted, versioned snapshot locally, upload to a temporary Dropbox
path, verify size/hash, then atomically promote it. Retain prior known-good generations and last
successful backup/verification metadata. Offline creation can queue upload without changing local
authority. Restore downloads and verifies before opening an isolated validation/import transaction.
This is suitable for single-user or server backups and does not create a shared database.

### B. Authoritative controlled single-user file — possible later, not preferred initially

Only one device may hold a renewable write lease. Each save uploads a complete immutable generation
with compare-and-swap revision metadata; conflicts create explicit divergent copies and stop writes.
Offline edits require an operation journal and merge semantics. Atomic temp-upload/promote, checksums,
and retained generations are mandatory. This is substantially more work than “store SQLite in
Dropbox” and is not suitable for household collaboration.

### C. Multi-device synchronization — requires a synchronization service

Dropbox file revisions alone cannot safely authorize or serialize concurrent allocations. A real
multi-device provider needs operation identities, ordering, conflict detection, permission enforcement,
actor identity, revocation, and push/poll semantics. It is effectively a shared authority and should
not be claimed until designed and tested as one. Directly opening one SQLite file from multiple
devices is explicitly prohibited by the product specification.
